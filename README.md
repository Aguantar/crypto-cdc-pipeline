# crypto-cdc-pipeline

[![CI](https://github.com/Aguantar/crypto-cdc-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/Aguantar/crypto-cdc-pipeline/actions/workflows/ci.yml)

미니 PC 한 대에서 두 거래소(Upbit, Binance)의 체결과 호가를 상시 수집하고, 그 값이 맞는지를 거래소가 공개한 캔들과 매일 대조하는 파이프라인입니다. 2026년 2월 13일부터 운영 중이고, 이 문서의 숫자는 2026년 10월 10일 기준입니다. 합성 데이터는 쓰지 않습니다.

이 저장소가 보여 주려는 것은 규모가 아니라 검증입니다. 무엇을 얼마나 받았는지보다 받은 값이 맞는지를 어떻게 아는지, 틀렸을 때 어떻게 알았는지를 기록했습니다.

## 증명하는 것

| 주장 | 근거 | 문서 |
|---|---|---|
| 유실은 지표가 아니라 대조가 찾는다 | 거래소 캔들과 마켓 × 시간 셀 단위로 매일 대조. 전체 비율 99.3% 안에 한 마켓 한 시간 50%가 숨어 있던 것을 셀 최소값이 잡았다 | [docs/19](docs/19-loss-prevention-gap-map.md) |
| 지연과 유실을 구분한다 | 적재량 반토막 사고를 적재 시각과 체결 시각 두 기준으로 다시 세어 36.9시간 지연으로 판정. 유실 0 | [docs/08](docs/08-ingest-lag-incident.md) |
| 중복은 저장소가 흡수한다 | exactly-once 대신 ReplacingMergeTree와 읽는 쪽 FINAL. 재기동 중복 239건이 0으로 | [docs/24](docs/24-broker-reduction-design.md) |
| 병목은 재서 특정한다 | 녹화 재생 부하 실험 500에서 10,000 rows/s. 병목은 Kafka가 아니라 동기 JDBC 싱크였고, 배치 1,000으로 정체 0 | [docs/23](docs/23-load-experiment-results.md) |
| 구성은 실측으로 줄인다 | 브로커 3에서 1로, Flink 잡 4에서 3으로. 둘 다 정지 실험과 병행 실험 뒤 | [docs/24](docs/24-broker-reduction-design.md), [docs/50](docs/50-binance-trade-mv.md) |
| 틀린 것을 찾아낸 기록이 있다 | 필터 하나가 체결의 52%를 버림, 품질 표가 16일간 안 돌았는데 아무도 몰랐음, 수집기가 5시간 살아 있는 척함, 백업이 7일간 원격에 안 갔는데 성공으로 찍힘. 넷 다 원인과 조치와 검증이 있다 | [docs/48](docs/48-silent-pipeline-incident.md), [docs/51](docs/51-backup-silent-failure.md) |

규모(평균 수백 events/s), 가용성(한 대), 분산과 클라우드 경험은 이 프로젝트로 말할 수 없습니다. 아래 `못 하는 것`에 적었습니다.

## 구조

```
[Upbit WS 체결 292마켓] --> producer --> MySQL(이벤트시각 일 파티션)
                                          | binlog
                                          v
                                     Debezium --> Kafka --> Flink --> ClickHouse
                                                             ^
[Upbit WS 호가] ----------------------------> Kafka ---------+   (원장 없이 직행)
[Binance WS 체결 502심볼] ------------------> Kafka --> ClickHouse Kafka 엔진 + MV   (Flink 잡에서 옮김)
[Binance WS depth 증분] --------------------> Kafka --> Flink 키별 상태로 호가장 재구성

[2층] Binance Testnet 주문 --> MySQL 미러 --> 2번째 Debezium(삭제 보존) --> ClickHouse RMT
```

체결과 호가의 경로가 다르고 Binance 체결은 Flink를 거치지 않습니다. 이유는 `결정`에 있습니다.

## 결정

결정마다 그때의 이유와 지금의 판단을 적었습니다. 판단은 맞았다, 필요했다, 과했다 셋 중 하나입니다.

| 결정 | 그때의 이유 | 지금의 판단 | 근거 |
|---|---|---|---|
| 미니 PC 한 대 | 비용 0, 이미 있던 기계 | 학습과 비용에는 맞았다. 가용성이 없는 이유의 전부다 | |
| MySQL 원장, Debezium, Kafka | 되돌릴 수 없는 데이터에 원본을 남긴다 | 맞았다. 브로커 전부 정지 실험 4회에서 체결을 지켰다 | [docs/24](docs/24-broker-reduction-design.md) |
| 가상 매매로 2층 원장 | 체결만으로는 CDC가 큐와 같아서 | 맞았다. 상태 변경을 거래소 엔진이 만든다. 3자 대조 불일치 0 | |
| Kafka | 버퍼, 오프셋 재개, 이미 있던 클러스터 | 필요했다. 브로커는 3에서 1로 줄였고 그 경계를 실험으로 쟀다 | [docs/24](docs/24-broker-reduction-design.md) |
| Flink | 이벤트 시각 처리와 키별 상태. 그리고 써 보고 싶었다 | 이 규모엔 과했다. 상태 없는 잡 하나를 ClickHouse MV로 옮겨 실측했다 | [docs/50](docs/50-binance-trade-mv.md) |
| ClickHouse | 시계열 집계에 흔히 쓰이고 한 대에서 큰 표를 버틴다고 알려져서 | 맞았다. 근거(압축 14:1, 선택적 읽기 7.5배)는 사후에 쟀고 대안과 비교한 적은 없다 | |
| ReplacingMergeTree와 FINAL | exactly-once 대신 저장소가 중복을 흡수 | 맞았다. 대가는 FINAL의 읽기 비용이고, 전체 이력 모델은 증분으로 바꿔야 했다 | [docs/48](docs/48-silent-pipeline-incident.md) |
| dbt | 변환에 테스트, 계약, 문서를 붙이려고 | 맞았다. 다만 테스트가 열흘 실패해도 dbt는 스스로 알리지 않는다 | [docs/48](docs/48-silent-pipeline-incident.md) |
| Airflow | 재시도, 백필, 풀, 실행 이력. 그리고 시장에서 기본이라 | 이 규모엔 cron으로도 된다. 실제로 쓴 기능이 있어 남겼고 비용은 스케줄러 메모리 | |
| 외부 감시자를 push로 | 죽은 쪽이 대답해야 하는 감시자는 감시자가 아니라서 | 맞았다. 훈련에서 899초 만에 판정 | [docs/32](docs/32-slo-and-alerting.md) |

세 결정은 설명이 더 필요합니다.

**체결은 INSERT뿐인데 CDC를 왜 쓰나.** 체결에는 UPDATE도 DELETE도 없어 CDC가 큐와 다를 게 없습니다. 구조를 바꾸는 대신 상태가 바뀌는 데이터를 직접 만들었습니다. Binance Testnet에 가상 매매 주문을 넣고 그 상태를 MySQL에 미러링한 뒤 두 번째 Debezium 커넥터로 삭제까지 캡처합니다. 상태를 바꾸는 주체가 우리가 아니라 거래소 엔진입니다. 커넥터는 두 모드입니다. 체결은 삭제를 버리는 아카이브 모드(삭제가 보존 정책이지 사실의 변화가 아니므로), 원장은 삭제를 보존하는 미러 모드.

**왜 체결과 호가의 경로가 다른가.** 되돌릴 수 있는지가 다릅니다. 체결은 거래소 이력 API와 MySQL 원장이 있어 7일 안에 복구되고, 호가는 둘 다 없어 못 받으면 영구 유실입니다. 그래서 체결은 Kafka 앞에 원장을 두고, 호가는 수집기 버퍼가 유일한 방어입니다. 이 판단은 실패에서 나왔습니다. 초기에 호가를 Kafka 직행으로 뒀다가 브로커 정지 실험에서 35,838건을 잃었고, 그 경험이 "체결도 Kafka 선기록으로"라는 계획을 철회시켰습니다.

**왜 Flink인가, 그리고 지금의 답.** 체결은 도착 순서가 뒤집히고 늦게 오는 행이 있어 이벤트 시각 처리가 필요했고, 호가장 재구성처럼 심볼별 상태를 들고 있어야 하는 잡이 있었습니다. 돌려 보고 잡별로 해체하니 판단이 바뀌었습니다. 체크포인트 상태가 CDC 잡 3.36 MiB, 호가장 재구성 0.33 MiB, 나머지 둘은 0에 가깝습니다. 파싱과 적재만 하는 잡은 ClickHouse의 Kafka 엔진과 Materialized View로 되고, 분 종가 판정은 1분 SQL로 됩니다. 그래서 가장 단순한 Binance 체결 잡을 옆에 세워 47시간 병행하고 옮겼습니다.

| | Flink 잡 | Kafka 엔진 + MV |
|---|---|---|
| 값 (24,262셀, 4,930만 행) | 기준 | 불일치 0, 중복 0 |
| 적재 지연 p95 | 2.90초 | 3.56초 |
| 파트 생성 / 머지 (48h) | 125,176 / 40,402 | 51,494 / 11,326 |
| ClickHouse 기준선 메모리 | 769 MiB | 847 MiB |

다시 고른다면 스트림 엔진 없이 저장소와 스케줄러가 대부분을 하게 두고, 키별 상태가 필요한 잡 하나만 가벼운 소비자로 둡니다. 남은 Flink 잡은 셋이고 한 번에 하나씩 뺍니다. 잡을 빼도 TaskManager의 1 GB는 JVM 설정값이라 줄지 않습니다.

## 값이 맞다는 것을 어떻게 아는가

**대조.** `dq_`로 시작하는 품질 표 9개가 매일 계산됩니다. 거래소 대조 두 종류, 적재 지연 분위수, 호가 공백 창, 수리 계보, 규칙 평가, 동등성, 원장 3자 대조, 수집 공백 라벨링. 공백 라벨링은 거래소 공지 1,200건을 수집해 붙였는데, 거래소의 점검 카테고리로 걸렀으면 실제 거래 중단 8건을 놓쳤을 것입니다.

**계약.** 소비자를 마주하는 모델 9개에 `contract: enforced`, 증분 모델에 `on_schema_change=fail`, 토픽에 JSON 스키마와 자체 시험이 있는 검증기. 계약은 도입 직후 어댑터의 타입 비교 방식 때문에 매일 빌드를 멈췄고, 어댑터를 올려 물리 타입 그대로 강제하게 한 뒤에야 진짜 불일치 한 건이 드러났습니다.

**감시.** 10분 헬스체크 15항목, 매시 품질 판정, 주 1회 다이제스트. 헬스체크에는 파생 표가 이틀 넘게 안 갱신되면, 오프사이트 백업이 이틀 넘게 안 도착하면, 원격 볼륨이 85%를 넘으면 울리는 항목이 있습니다. 같은 이름은 시간당 한 번만 보내고, 유입이 멈추는 종류가 30분 넘게 지속되면 휴대폰 알림을 켠 별도 채널로 승격합니다. 수집기가 5시간 살아 있는 척한 날 일반 채널에 5번 울렸는데 아무도 보지 않았기 때문입니다. 감시자는 다른 기계에 있고 push 방식입니다.

**메모리 예산.** 서버 한도 1.57 GiB에서 기준선 0.8 GiB와 머지 버스트 0.6 GiB를 빼면 쿼리 몫이 나오고, 전체 이력을 매일 다시 읽는 모델은 거기서 죽습니다. 그런 모델 셋을 이틀 증분으로 바꿨습니다(1.46 GiB가 338 MiB로).

## 배운 것

사고와 결정에서 남은 규칙입니다. 번호는 위 표의 사건입니다.

| 규칙 | 어디서 |
|---|---|
| 유실은 지표가 아니라 대조가 찾는다. 수집기 카운터는 급등 손실도 5시간 정지도 보지 못했다 | 5, 6 |
| 검증은 행 수가 아니라 값으로 한다. 행 수는 같은데 합계가 2e-8 다른 것이 Decimal 버림이었다 | 1 |
| 만든 것과 도는 것은 다르다. 완료는 스케줄 실행 이력과 전수 쿼리와 자체 시험으로만 말한다 | 4 |
| 도구는 어디서나 같은 버전이어야 한다. 호스트의 다른 버전 dbt가 "통과"를 만들었고, CI는 옛 버전으로 엿새 동안 빨갛게 있었다 | 4 |
| 살아 있나와 맞나는 다른 질문이다. 원본 적재 감시는 파생 표의 정지를 못 본다 | 4, 7 |
| 열려 있는 소켓은 살아 있다는 뜻이 아니다. 데이터가 와야 산 것이고, 안 오면 스스로 끊는다 | 5 |
| 사건과 상태를 구분한다. 같은 상태를 10분마다 다시 보내면 사람이 알림을 끈다. 30분 넘게 지속되는 critical은 사람에게 닿는 채널로 승격한다 | 4, 5 |
| 자원이 빠듯하면 예산은 쿼리 한도가 아니라 총량에서 기준선과 버스트를 뺀 것이다 | 4 |
| 규모에 맞게 고르고, 잘못 고른 것은 재서 뒤집는다. Flink 잡 하나를 47시간 병행 뒤 옮겼다 | 결정 표 |
| 되돌릴 수 있는 데이터와 없는 데이터를 같게 다루지 않는다. 호가 35,838건을 잃고 배웠다 | 결정 표 |
| 백업은 복원해 보기 전까지 백업이 아니다. 파이프 뒤의 명령이 종료 코드를 정하고, 검증은 정리에 종속시키지 않는다 | 7 |
| 첫날 숫자를 외삽하지 않는다. 증분 80MB가 보름 뒤 16GB가 됐다. 보존은 날짜와 GB 둘 다로 검산한다 | 7 |
| 테스트가 막을 수 있는 것은 그 시각에 판정할 수 있는 것뿐이다. 거래소 캔들이 아직 없는 시각의 공백 테스트는 경고여야 한다 | 8 |

## 못 하는 것

- 규모가 크지 않습니다. 평균 수백 events/s. 규모 이야기는 부하 실험 문장으로만 합니다.
- 분산 처리를 해본 적이 없습니다. 단일 호스트, 단일 브로커.
- 가용성이 없습니다. 이 기계가 죽으면 전부 멈추고 복구는 수동입니다. 외부 감시자는 15분 안에 안다는 것이지 안 죽는다는 것이 아닙니다.
- 영구 보존이 없습니다. Binance 체결은 30일, 호가 원본은 Parquet으로 60일까지입니다. 그 뒤는 어디에도 없습니다.
- Binance 체결은 재수집 수단이 없습니다. 재연결 공백은 그대로 손실이고 대조가 다음날 숫자로 알려 줄 뿐입니다.
- Kafka 인증이 없습니다. 방화벽과 로컬 바인딩으로 막았습니다.
- 소비자가 저 자신입니다. 실제 이해관계자의 요구사항을 받아본 것은 아닙니다.

## 예상 질문

- **이 규모에 Kafka가 필요한가.** 분산이 아니라 로그의 성질 때문입니다. 오프셋 재개, 다중 소비자, 키 순서. 재처리 런북이 특정 구간을 같은 잡으로 다시 흘리는 것이 오프셋 재개 덕입니다.
- **중복이 239건 있다면 값을 못 믿는 것 아닌가.** at-least-once의 정상 동작입니다. 막는 대신 저장소가 흡수하고 읽는 쪽이 FINAL로 보장합니다. 대가는 FINAL의 읽기 비용이고, 그것 때문에 전체 이력 모델 셋을 증분으로 바꿨습니다.
- **ClickHouse를 컬럼 지향 때문에 골랐나.** 아닙니다. 이 프로젝트에서 컬럼 지향의 이점을 크게 쓰는 쿼리는 대조 하나입니다. 진짜 근거는 압축과 정렬 키로 한 대에서 버틴다는 자원 논리이고, 그것도 사후에 쟀습니다.
- **Airflow를 왜 썼나.** 이 규모엔 cron으로도 됩니다. 코인 292개를 동적으로 펼치는 품질검증, 거래소 REST 한도를 지키는 풀, 과거 날짜 백필을 실제로 써서 남겼습니다. 잘못 쓴 설정(`depends_on_past`)이 파이프라인을 멈추기도 했습니다.
- **가장 큰 실수는.** 계약과 테스트 수정을 호스트의 다른 버전 dbt로 검증하고 "통과"라 적은 것입니다. 스케줄 실행은 컨테이너의 옛 어댑터로 매일 실패했고 열엿새를 몰랐습니다.
