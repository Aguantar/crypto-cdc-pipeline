# crypto-cdc-pipeline

미니 PC 한 대에서 암호화폐 거래소의 실데이터를 상시 수집하고, 그 값이 맞는지를 거래소가 공개한
정답과 대조해 증명하는 파이프라인입니다. 2026년 2월 13일에 첫 데이터가 들어왔고 오늘로 221일째
돌고 있습니다. 합성 데이터는 쓰지 않습니다.

돌아가는 파이프라인을 만드는 것과 값이 맞는 파이프라인을 만드는 것은 다른 일이라고 생각해서
시작했습니다. 튜토리얼 파이프라인 대부분은 정확성을 재지 않습니다. 데이터를 넣고 대시보드를
띄우면 끝이고, 틀렸는지 맞았는지는 만든 사람도 모릅니다. 그래서 처음부터 조건을 세 개 걸었습니다.

- 합성 데이터를 쓰지 않는다. Faker 로 만든 데이터는 유실도 지연도 중복도 만들지 않아서 고칠 문제가 생기지 않습니다.
- 정답이 밖에 있어야 한다. 거래소가 1분·1시간 캔들로 체결 수를 공개하므로 내 집계를 남의 정답과 맞춰볼 수 있습니다.
- 되돌릴 수 없는 데이터를 다룬다. 호가는 이력 API 가 없어서 못 받은 순간 영구 유실입니다. 다시 받으면 된다가 통하지 않아야 설계가 진지해집니다.

## 구조

```
[Upbit WS 체결] --> producer --> MySQL(이벤트시각 일 파티션)
                                   | binlog
                                   v
                              Debezium --> Kafka --> Flink --> ClickHouse
                                                      ^
[Upbit WS 호가] ----------------------> Kafka --------+   (원장 없이 직행)
[Binance WS 체결 493심볼] -------------> Kafka --------+
[Binance WS depth 증분] ---------------> Kafka --> Flink 키별 상태로 호가장 재구성

[2층] Binance Testnet 주문 --> MySQL 미러 --> 2번째 Debezium(삭제 보존) --> ClickHouse RMT
```

같은 파이프라인 안에서 체결과 호가의 경로가 다릅니다. 보통은 일관성이 없다고 지적받는 지점인데,
두 데이터의 되돌릴 수 있음이 다르기 때문입니다. 체결은 거래소 이력 API 와 우리 MySQL 원장이
둘 다 있어서 7일 안이면 복구되지만, 호가는 어느 쪽도 없습니다. 그래서 체결은 Kafka 앞에 MySQL
원장을 둬서 브로커가 전부 죽어도 원본이 남게 했고, 호가는 수집기 버퍼가 유일한 방어입니다.

이 판단은 실패에서 나왔습니다. 초기에 호가를 Kafka 직행 구조로 뒀다가 35,838건을 잃었고,
그 경험이 "체결도 Kafka 선기록으로 바꾸자"는 계획을 철회시켰습니다. 앞에 두면 MySQL 이라는
안전망이 사라지기 때문입니다.

국소 유실을 가린 사례를 겪고 나서 기준을 바꿨습니다.

## 설계에서 고른 것들

### Kafka 를 쓰는 이유, 그리고 브로커를 3대에서 1대로 줄인 이유

초당 수백에서 1,300건입니다. 분산이 필요한 규모가 전혀 아니라서 이 규모에 Kafka 가 왜 필요하냐는
질문은 정당합니다. 그래서 근거를 분산이 아니라 로그의 성질로 잡았습니다. 오프셋 재개, 다중 소비자,
키 단위 순서 보장은 규모와 무관하게 필요합니다.

같은 논리로 브로커를 줄였습니다. 3브로커가 같은 호스트, 같은 NVMe, 같은 커널 위에 있으면
디스크나 전원이나 재부팅은 셋을 같이 죽입니다. 복제본 개수는 내구성이 아니고 장애 도메인을
넘어야 복제입니다.

줄이기 전에 브로커를 전부 멈춰놓고 각 경로가 어디서 버티고 어디서 무너지는지 쟀습니다.
체결은 MySQL 원장이 네 번 모두 지켰고 호가는 수집기 버퍼가 10분까지 지켰습니다. 그 뒤
105개 파티션을 무정지로 재할당했고, 축소 후 재기동을 한 번 더 실측했습니다.

| 축소 후 재기동 실측 | 결과 |
|---|---|
| 브로커 응답까지 | 14초 |
| 유실 | 0 (체결·호가 모두) |
| 중복 | 239건 (at-least-once 재전송) |
| 그날 거래소 대조 | 6,803셀 전부 100% |

받아들인 위험은 명확합니다. 브로커 1대 정지가 곧 전체 정지이고, 10분을 넘기면 호가 유실이
시작됩니다. `dq_orderbook_gaps_daily` 가 그 결과를 셉니다.

### CDC 를 의미 있게 만든 방법

체결 데이터는 INSERT 뿐입니다. UPDATE 도 DELETE 도 없으니 CDC 가 큐와 다를 게 없고,
CDC 파이프라인이라는 이름이 무색해집니다.

구조를 바꾸는 대신 상태가 바뀌는 데이터를 직접 만들었습니다. Binance Testnet 에 가상 매매
주문을 넣고 그 주문 상태를 MySQL 에 미러링한 뒤, 두 번째 Debezium 커넥터로 삭제까지
캡처했습니다. 여기서 중요한 것은 상태를 바꾸는 주체가 우리가 아니라 거래소 엔진이라는 점입니다.
우리가 우리 DB 를 UPDATE 하는 것은 CDC 의 의미가 아닙니다.

그래서 커넥터를 두 모드로 나눠 씁니다. 체결은 `skipped.operations=d` 로 삭제를 버리는 아카이브
모드입니다. 삭제가 보존 정책이지 사실의 변화가 아니기 때문입니다. 원장과 케이스는 삭제를
보존하는 미러 모드입니다. 취소와 삭제가 사실 그 자체이기 때문입니다.

### 금액은 Decimal, 비율은 Float64

처음에는 전부 Float64 였고, 대조가 통과하고 있었으므로 문제를 몰랐습니다. 월별 금액 합이
원본보다 2e-8 작게 나오면서 드러났습니다. 행 수와 수량 합은 정확히 같았습니다.

원인은 ClickHouse 의 `CAST(Float64 -> Decimal)` 이 반올림이 아니라 버림이라는 것이었습니다.
금액과 수량은 Decimal, 비율과 파생지표는 Float64 로 규칙을 정하고, 변환은 문자열을 거치도록
(`toDecimal128(toString(x), 8)`) 바꿨습니다. 표 재생성은 `EXCHANGE TABLES` 런북으로 적재를
멈추지 않고 했습니다.

이 건 이후로 검증 기준을 행 수에서 값으로 바꿨습니다.

### 중복을 막지 않고 흡수한 이유

브로커 재기동에서 중복 239건이 확인됐습니다. at-least-once 의 정상 동작입니다. 중복을 없애려고
exactly-once 를 맞추면 전체 구조가 무거워지는데, 이 규모에서는 값을 못 합니다.

그래서 ReplacingMergeTree 로 저장하고 읽는 쪽이 FINAL 로 보장하는 방식을 골랐습니다.
RMT 는 결국 중복을 제거하기 때문에 머지 전에 읽으면 중복이 보입니다. RMT 를 읽는 모델
7개 전부에 FINAL 을 붙였습니다.

검증하다 제 검증이 틀린 것도 발견했습니다. 두 행을 한 INSERT 로 넣으면 RMT 가 삽입 시점에
이미 접어버려서 원본이 2가 아니라 1이었습니다. 별도 INSERT 두 번으로 다시 해야 증거가 됐습니다.

### Airflow 에서 쓰지 않기로 한 것들

쓰는 이유는 흔하니 안 쓴 것과 그 이유를 적습니다.

- Celery, Kubernetes Executor: 1호스트 16GB, 동시 태스크 8에서는 관리 비용만 늘어납니다.
- 외부 스토리지 센서: 기다릴 외부 적재가 없습니다. 생산자를 우리가 소유합니다.
- 캔들 존재 센서: 대조 DAG 이 스스로 REST 로 캔들을 받고 한 마켓이라도 실패하면 예외를 던지므로 이미 하드 게이트입니다. 센서를 넣으면 기다리는 시늉만 하고 워커 슬롯을 먹습니다.
- Slack Provider: 웹훅이 이미 Airflow Variable 에 있고, 지금 겪는 문제가 아닌데 의존성을 늘릴 이유가 없습니다.

## 값이 맞다는 것을 어떻게 아는가

`dq_` 로 시작하는 품질 표 9개가 매일 계산됩니다. 거래소 대조 두 종류, 적재 지연 분위수,
호가 공백 창, 수리 계보, 규칙 평가, 동등성, 원장 3자 대조, 그리고 수집 공백 라벨링입니다.

마지막 것은 설명이 필요합니다. 공백을 세는 것만으로는 사고인지 점검인지 알 수 없습니다.
거래소 점검 중에는 체결이 없는 것이 정상입니다. 그래서 거래소 공지 1,200건을 수집해 공백에
라벨을 붙였는데, 거래소가 붙인 점검 카테고리는 대부분 신분증이나 원화 입출금이라 거래를
멈추지 않았습니다. 카테고리로 걸렀으면 실제 거래 중단 8건을 놓쳤을 것입니다.

계약도 걸어뒀습니다. 컬럼 이름을 한 번 바꿨다가 대시보드 패널 10개를 죽인 적이 있어서,
소비자를 마주하는 모델 9개에 `contract: enforced` 를 붙였습니다. 컬럼 이름을 일부러 바꿔서
빌드가 실제로 멈추는지 확인했습니다. 증분 모델은 `on_schema_change=fail` 입니다.
`append_new_columns` 는 조용히 늘린다는 뜻이라 계약의 취지에 반합니다.

토픽에도 JSON 스키마 계약이 있고, 검증기(`scripts/ops/validate-topic-schemas.py`)에는
`--self-test` 가 있습니다. 검증기가 위반을 실제로 잡는지 먼저 시험하지 않으면
통과만 하는 검증기가 되기 때문입니다.

## 겪은 문제 몇 가지

**필터 하나가 진짜 체결 3만 행을 버리고 있었다.** 모델마다 체결을 거르는 조건이 제각각이라
통일하려고 대조하다 발견했습니다. `op = 'c'` 만 통과시키고 있었는데 CDC 에는 스냅샷(`r`)과
백필도 있습니다. 6월 27일 두 시간 창에서 6,696행이 13,984행이 됐습니다. 그 창에서 체결의
52% 가 사라지고 있었습니다. 고친 뒤 늘어난 양이 원인과 정확히 일치하는지로 검증했습니다.
`int_ohlcv_daily` 의 2월 13일이 186,388에서 209,488로 23,100 늘었는데, 그날 `op='r'` 행 수와
같은 값입니다. 늘어난 것이 중복이 아니라 빠져 있던 진짜 체결이라는 증거입니다.

**3자 대조가 열린 날에는 항상 불일치였다.** 대시보드에 붙이자마자 5심볼 전부 빨강이었는데
실제 데이터는 멀쩡했습니다. 두 값의 측정 시각이 달랐던 것이고, 스냅샷과 실시간을 비교하고
있었습니다. 열마다 다른 기준 시각으로 상한을 걸어서 불일치를 0으로 만들었습니다. 거짓 경보를
내는 대조는 대조가 아닙니다. 사람이 곧 빨강을 무시하게 됩니다.

**부하 실험에서 병목은 Kafka 가 아니었다.** Binance 공개 체결을 녹화해 500부터 10,000 rows/s 까지
계단으로 재생했습니다. Kafka 는 무배치 acks=all 로 19k/s, 배치로 65k/s 가 나와서 파이프라인
계단의 100배에서 300배였습니다. 진짜 병목은 소스 체인에 묶인 동기 JDBC 싱크였고, 근거 셋을
각각 측정했습니다. 정체 창이 ClickHouse insert 지연이 오른 분과 일치했고, 서브태스크 busy 가
inserts/s 곱하기 insert 지연과 맞았고, ClickHouse CPU 의 대부분이 머지였습니다. 싱크 배치를
200에서 1,000으로 바꾸자 정체 창이 5에서 0이 됐습니다. 유실 없이 실시간을 유지한 최대는
5,000 rows/s 로 관찰 주간 피크의 85배입니다.

**만든 것과 도는 것은 다르다.** 하루에 같은 유형을 다섯 번 만났습니다. DAG 네 개가 만들어진 뒤
한 번도 안 돌고 있었고, 재배포 스크립트는 옛 JAR 을 배포하면서 성공이라고 찍었고, 방화벽
스크립트는 한 번도 실행된 적이 없어 버그 두 개가 잠복해 있었고, Prometheus 대시보드 12패널이
통째로 빈 화면이었고, cron 하나가 옛 비밀번호로 매분 403을 내고 있었습니다.

그래서 만들었다는 말을 스케줄 실행 이력, 전수 쿼리 실행, 자체 시험으로만 하기로 했습니다.

## 감시와 알림

알림은 세 층입니다. 10분마다 도는 헬스체크 12항목, 매시 도는 품질 SLO 판정, 주 1회 다이제스트입니다.
품질 게이트 임계를 0건이 아니라 90%로 둔 이유는, 얇은 마켓 한두 개가 순간적으로 조건을 못 맞추는
일이 늘 있고 그때마다 리포트를 막으면 사람이 게이트를 꺼버리기 때문입니다. 다만 중복 적재는
0건이 아니면 무조건 차단합니다. 정도의 문제가 아니라 사고입니다.

감시자는 다른 기계에 있습니다. 알림을 보내는 DAG 다섯 개가 전부 감시 대상인 미니 PC 안에서
돌고 있었는데, 그 기계가 죽으면 알림도 같이 죽습니다. 실제로 보안 하드닝으로 ClickHouse 포트를
로컬 바인딩으로 좁혔다가 바깥에서 감시하던 워크플로의 경로를 끊었고, 8시간 38분 동안 매분
에러만 쌓이고 알림은 0건이었습니다.

구조 자체도 문제였습니다. 그 감시자는 미니 PC 에 질의해서 최근 유입이 0인지 보는 pull 방식이라,
통째로 죽으면 질의가 실패해 판정에 도달하지 못합니다. 죽었다고 알리려면 죽은 쪽이 대답해줘야
하는 감시자였습니다.

포트를 다시 여는 대신 방향을 뒤집었습니다. 미니 PC 의 호스트 cron 이 5분마다 상태를 바깥으로
push 하고, 받는 쪽은 파일의 나이만 봅니다. 파일이 갱신되지 않은 것 자체가 신호라서 죽은 쪽의
협조가 필요 없습니다. 보내는 쪽을 Airflow DAG 이 아니라 호스트 cron 에 둔 것도 같은 이유입니다.
보내는 쪽은 감시 대상보다 의존성이 적어야 합니다.

훈련으로 확인했습니다. 송신을 끊고 임계 전에 두 번 조용한 것을 본 뒤, 899초 만에 판정이 나고
Slack 이 실제로 도착하는 것까지 쟀습니다. 재개 4초 만에 복구 알림이 왔습니다.
훈련 스크립트(`scripts/ops/watchdog-drill.sh`)는 언제든 다시 돌릴 수 있습니다.

## 못 하는 것

이 항목이 있어야 나머지 숫자가 신뢰를 얻는다고 생각합니다.

- 규모가 크지 않습니다. 상시 수백에서 1,300 events/s 이고, 6.5억 행은 실무 기준으로 중간 규모의 하루치입니다. 규모 이야기는 부하 실험 문장으로만 합니다.
- 분산 처리를 해본 적이 없습니다. 단일 호스트, 단일 브로커입니다. 분산이 필요한 지점과 손댈 순서를 실측으로 안다고 말하지, 해봤다고 하지 않습니다.
- 가용성이 없습니다. 이 기계가 죽으면 전부 멈추고 복구는 수동입니다. 외부 감시자는 관측 가능성을 장애 도메인 밖으로 뺀 것이지 가용성이 아닙니다. 죽으면 15분 안에 안다와 안 죽는다는 다른 문장입니다.
- 대규모 배치를 운영한 적이 없습니다. DAG 11개와 dbt 모델 27개는 돌고 있지만 대규모가 아닙니다.
- Kafka 인증이 없습니다. 방화벽과 로컬 바인딩으로 막았고, SASL 은 클라이언트가 10곳 이상이라 미뤘습니다.
- 소비자가 저 자신입니다. 2층 원장과 케이스 관리로 소비자를 만들어 대조 대상을 만들었지만, 실제 이해관계자의 요구사항을 받아본 것은 아닙니다.

## 실행

```bash
cp .env.example .env     # 값을 채웁니다
docker compose up -d     # 기본 18개 서비스
scripts/build-flink-job.sh
scripts/startup.sh       # 토픽·커넥터·Flink 잡 등록
scripts/check-health.sh
```

`--profile ops` 를 붙이면 kafka-ui 와 Prometheus 가 같이 뜹니다. 평소에는 내려둡니다.
Airflow 스케줄러 OOM 사고 때 Prometheus 360MB 가 대시보드 하나를 위해 떠 있었다는 것이
근거였습니다.
