# crypto-cdc-pipeline

[![CI](https://github.com/Aguantar/crypto-cdc-pipeline/actions/workflows/ci.yml/badge.svg)](https://github.com/Aguantar/crypto-cdc-pipeline/actions/workflows/ci.yml)

미니 PC 한 대에서 암호화폐 거래소의 실데이터를 상시 수집하고, 그 값이 맞는지를 거래소가 공개한
정답과 대조해 증명하는 파이프라인입니다. 2026년 2월 13일에 첫 데이터가 들어왔고 오늘로 221일째
돌고 있습니다. 합성 데이터는 쓰지 않습니다.

**여섯 줄 요약**

1. 값이 맞는지를 거래소 캔들과 **마켓 × 시간 셀 단위**로 매일 대조합니다. 전체 비율은 국소 유실을 가리기 때문입니다.
2. 체결과 호가의 경로가 다릅니다. **되돌릴 수 있는 데이터와 없는 데이터를 같게 다루지 않습니다.**
3. 코어 4개 RAM 16GB 한 대입니다. 스택 선택이 거의 다 이 제약에서 나왔고, **뺀 것에도 근거와 숫자**가 있습니다.
4. 상태가 바뀌는 데이터가 없어서 **가상 매매로 직접 만들었습니다.** 체결은 INSERT 뿐이라 CDC 가 큐와 다를 게 없었습니다.
5. **틀렸던 것도 적어뒀습니다.** 필터 하나가 특정 두 시간 창에서 체결의 52% 를 버리고 있었습니다.
6. 못 하는 것: 가용성 없음, 분산 경험 없음, 대규모 배치 없음. 아래에 그대로 적었습니다.

바쁘시면 `왜 이렇게 했나` 와 `한 대짜리 기계가 무엇을 사고 무엇을 뺐나` 두 절만 보셔도 됩니다.


## 구조

```
[Upbit WS 체결] --> producer --> MySQL(이벤트시각 일 파티션)
                                   | binlog
                                   v
                              Debezium --> Kafka --> Flink --> ClickHouse
                                                      ^
[Upbit WS 호가] ----------------------> Kafka --------+   (원장 없이 직행)
[Binance WS 체결 493심볼] -------------> Kafka --------+
[Binance WS depth 증분] ---------------> Kafka --> Flink 키별 상태로 호가장 재구성

[2층] Binance Testnet 주문 --> MySQL 미러 --> 2번째 Debezium(삭제 보존) --> ClickHouse RMT
```

체결과 호가의 경로가 다릅니다. 의도한 것이고 이유는 아래 "왜 이렇게 했나"에 있습니다.

## 무엇이 저장되나

ClickHouse 표 61개 중 중심이 되는 것들입니다. 전체 목록과 컬럼 뜻은 [docs/35](docs/35-data-inventory.md)
와 dbt 문서에 있습니다.

| 표 | 한 행 = | 행 수 | 크기 | 엔진 / 정렬 키 |
|---|---|---|---|---|
| `crypto_trades` | Upbit 체결 한 건 | 1.20억 | 4.31 GiB | RMT / market, upbit_timestamp, sequential_id |
| `orderbook_raw` | Upbit 호가 스냅샷 한 건 | 1.37억 | 4.96 GiB | MergeTree / market, ts |
| `binance_trades` | Binance 체결 한 건 | 4,958만 | 1.01 GiB | RMT / symbol, trade_ms, trade_id |
| `orderbook_1m` | 마켓 × 1분 호가 집계 | 494만 | 411 MiB | MergeTree / market, window_start |
| `mart_trade_orderbook_1m` | 마켓 × 1분 체결·호가 결합 | 547만 | 451 MiB | MergeTree / market, minute |
| `upbit_hourly_candles` | 거래소 정답 (대조 기준) | 8.2만 | 2.27 MiB | RMT / market, hour_utc |

dbt 모델 27개는 층으로 나뉩니다. staging 2 (원본을 읽는 유일한 층), intermediate 7, dimensions 5,
marts 2, signals 2, quality 9. 품질 표는 전부 `dq_` 로 시작합니다.

## 왜 이렇게 했나

### "체결은 INSERT 뿐인데 CDC 를 왜 쓰나"

맞는 지적입니다. 체결 데이터에는 UPDATE 도 DELETE 도 없어서 CDC 가 큐와 다를 게 없습니다.
이름만 CDC 파이프라인이 됩니다.

구조를 바꾸는 대신 상태가 바뀌는 데이터를 직접 만들었습니다. Binance Testnet 에 가상 매매 주문을
넣고 그 주문 상태를 MySQL 에 미러링한 뒤, 두 번째 Debezium 커넥터로 삭제까지 캡처했습니다.
여기서 중요한 것은 상태를 바꾸는 주체가 우리가 아니라 거래소 엔진이라는 점입니다. 우리가 우리
DB 를 UPDATE 하는 것은 CDC 의 의미가 아닙니다.

커넥터를 두 모드로 나눠 씁니다. 체결은 `skipped.operations=d` 로 삭제를 버리는 아카이브 모드입니다.
삭제가 보존 정책이지 사실의 변화가 아니기 때문입니다. 원장과 케이스는 삭제를 보존하는 미러 모드입니다.
취소와 삭제가 사실 그 자체이기 때문입니다.

결과는 거래소와 MySQL 과 ClickHouse 사이 3자 대조 불일치 0입니다.

### "이 규모에 Kafka 가 필요한가"

초당 수백에서 1,300건입니다. 분산이 필요한 규모가 아니라서 정당한 질문입니다.

그래서 근거를 분산이 아니라 로그의 성질로 잡았습니다. 오프셋 재개, 다중 소비자, 키 단위 순서
보장은 규모와 무관하게 필요합니다. 실제로 재처리 런북(`scripts/ops/reprocess-day.sh`)이 특정 구간을
같은 Flink 잡으로 다시 흘리는데, 이게 가능한 이유가 오프셋 재개입니다.

### "왜 체결과 호가의 경로가 다른가"

두 데이터의 되돌릴 수 있음이 다르기 때문입니다.

| | 체결 | 호가 |
|---|---|---|
| 거래소 이력 API | 있음 | 없음 |
| 우리 원장 | MySQL 에 있음 | 없음 |
| 못 받으면 | 7일 안에 복구 가능 | 영구 유실 |

그래서 체결은 Kafka 앞에 MySQL 원장을 둬서 브로커가 전부 죽어도 원본이 남게 했고, 호가는 수집기
버퍼가 유일한 방어입니다.

이 판단은 실패에서 나왔습니다. 초기에 호가를 Kafka 직행 구조로 뒀다가 35,838건을 잃었고, 그
경험이 "체결도 Kafka 선기록으로 바꾸자"는 계획을 철회시켰습니다. 앞에 두면 MySQL 이라는 안전망이
사라지기 때문입니다.

### "중복이 239건 있다면 값을 못 믿는 것 아닌가"

at-least-once 의 정상 동작입니다. 중복을 없애려고 exactly-once 를 맞추면 전체 구조가 무거워지는데,
이 규모에서는 값을 못 합니다.

그래서 막는 대신 흡수합니다. ReplacingMergeTree 로 저장하고 읽는 쪽이 FINAL 로 보장합니다.
RMT 는 결국 중복을 제거하기 때문에 머지 전에 읽으면 중복이 보입니다. RMT 를 읽는 모델 7개
전부에 FINAL 을 붙였습니다.

검증하다 제 검증이 틀린 것도 발견했습니다. 두 행을 한 INSERT 로 넣으면 RMT 가 삽입 시점에 이미
접어버려서 원본이 2가 아니라 1이었습니다. 별도 INSERT 두 번으로 다시 해야 증거가 됐습니다.

### 그 밖에

**금액은 Decimal, 비율은 Float64.** 처음에는 전부 Float64 였고 대조가 통과하고 있었으므로 문제를
몰랐습니다. 월별 금액 합이 원본보다 2e-8 작게 나오면서 드러났는데, 행 수와 수량 합은 정확히
같았습니다. 원인은 ClickHouse 의 `CAST(Float64 -> Decimal)` 이 반올림이 아니라 버림이라는 것이었습니다.
표 재생성은 `EXCHANGE TABLES` 런북으로 적재를 멈추지 않고 했습니다. 이 건 이후로 검증 기준을
행 수에서 값으로 바꿨습니다.

**Airflow 에서 안 쓴 것들.** Celery 나 Kubernetes Executor 는 1호스트 16GB, 동시 태스크 8에서 관리
비용만 늘어납니다. 외부 스토리지 센서는 기다릴 외부 적재가 없어서 뺐습니다. 생산자를 우리가
소유합니다. 캔들 존재 센서도 뺐는데, 대조 DAG 이 스스로 REST 로 캔들을 받고 한 마켓이라도 실패하면
예외를 던지므로 이미 하드 게이트이기 때문입니다. 센서를 넣으면 기다리는 시늉만 하고 워커 슬롯을 먹습니다.

## 한 대짜리 기계가 무엇을 사고 무엇을 뺐나

코어 4개에 RAM 16GB 입니다. 스택 선택이 거의 다 이 제약에서 나왔고, 그래서 각 구성이 얼마를
쓰는지와 무엇을 사는지를 같이 적습니다.

### 가장 크게 산 것: ClickHouse

1.37 GiB 를 쓰고 두 가지를 삽니다.

**압축.** 호가는 거래소 이력 API 가 없어서 못 받으면 영구 유실입니다. 최대한 오래 원본으로
들고 있어야 하는데 하루 2천만 스냅샷이고 기계는 한 대입니다.

| 표 | 원본 | 디스크 | 비율 |
|---|---|---|---|
| `orderbook_raw` | 71.79 GiB | 4.97 GiB | 14.5:1 |
| `crypto_trades` | 21.75 GiB | 4.31 GiB | 5:1 |
| `binance_trades` | 4.61 GiB | 1.03 GiB | 4.5:1 |

이게 없었으면 보존 기간을 줄이거나 샘플링을 했을 텐데, 둘 다 되돌릴 수 없는 데이터에는
하면 안 되는 선택입니다.

**읽는 양.** `crypto_trades` 는 21개 컬럼인데 매일 도는 대조 쿼리는 4개만 씁니다. 같은 행
범위로 재보면 이렇습니다.

| 같은 3.13M 행 | 읽은 바이트 | 시간 |
|---|---|---|
| 컬럼 3개 | 75.31 MiB | 0.087초 |
| 전체 21개 | 563.46 MiB | 0.454초 |

저장 기준으로도 대조가 쓰는 4개 컬럼은 표 4.31 GiB 중 501.75 MiB, 11.6% 뿐입니다. 무거운
컬럼(`trade_amount` 21%, `sequential_id` 13.7%)은 정확히 대조가 안 쓰는 것들입니다.

**대가는 머지입니다.** 최근 24시간에 머지 134,500회, 25.1억 행을 읽었고 1.7 코어시간을 썼습니다.
파트는 초당 4.4개 생깁니다. 코어 4개에서 ClickHouse 단독 CPU 가 파이프라인 최대 소비자이고,
부하 실험에서 나온 병목도 결국 파트를 초당 50개 만드는 것이었습니다.

**안 골랐을 조건도 분명합니다.** 건별 조회나 갱신이 주 패턴이면 안 씁니다. 실제로 이 프로젝트의
주문 원장은 상태가 자주 바뀌어서 ClickHouse 가 아니라 MySQL 에 둡니다.

다만 대안을 실제로 돌려본 적은 없습니다. 위 숫자는 전부 221일 운영하고 나서 나온 사후 측정이고,
TimescaleDB 나 다른 컬럼 저장소와 비교한 실측은 없습니다.

### 자원 배분

최근 24시간 평균입니다(5분 간격 289 표본). 순간값은 머지 때문에 크게 흔들려서 평균으로 적습니다.

| 구성 | MEM | CPU | 무엇을 사는가 |
|---|---|---|---|
| ClickHouse | 1,292 MB | 138.9% | 압축 14.5:1, 선택적 읽기 7.5배 |
| Flink TaskManager | 1,118 MB | 15.9% | 키별 상태와 체크포인트 |
| MySQL | 919 MB | 2.3% | binlog 원장. 브로커가 전부 죽어도 체결이 남습니다 (정지 실험 4/4) |
| Kafka | 765 MB | 56.0% | 오프셋 재개, 다중 소비자, 키 순서 |
| Airflow 스케줄러 | 605 MB | - | 의존성 체인, 재시도, 실행 이력, 백필 |
| 수집기 4종 | 213 MB | 36.6% | WebSocket 수신과 파싱 |
| ZooKeeper | 112 MB | 0.1% | Kafka 메타데이터 |
| Grafana | 75 MB | 0.1% | 대시보드 2개 |

합계 CPU 는 코어 4개(400%) 중 249.6% 입니다.

두 가지가 눈에 띕니다. 하나는 ClickHouse 가 CPU 의 절반을 넘게 쓴다는 것이고, 대부분이 머지입니다.
산 것이 압축인데 그 값을 CPU 로 치르고 있는 셈입니다.

다른 하나는 Flink 입니다. TaskManager 가 1,118 MB 를 쓰는데 CPU 는 15.9% 뿐이고, 잡 다섯 개의
체크포인트 상태를 다 합쳐도 3.8 MiB 입니다. 즉 이 1 GB 는 상태 크기가 아니라 JVM 설정값
(`taskmanager.memory.process.size: 2g`)입니다. 상태 4 MiB 를 위해 RAM 1 GB 를 잡아두고 있는 것이고,
16 GB 기계에서 이건 다시 볼 만한 항목입니다.

### 뺀 것

| 뺀 것 | 회수 | 근거 |
|---|---|---|
| Kafka 브로커 2·3 | RAM 1.5GB, 디스크 27GB | 같은 호스트·같은 디스크라 RF3 이 형식뿐이었습니다. 정지 실험으로 각 경로가 어디까지 버티는지 확인한 뒤 |
| Prometheus + statsd-exporter | 360 MB | 대시보드 하나를 위한 비용이었습니다. 같은 날 있었던 Airflow 스케줄러 OOM 사고가 근거 |
| kafka-ui | 컨테이너 1개 | CLI 로 전부 하고 있어 장식이었고, 웹 UI 라 노출 면적이기도 했습니다 |

컨테이너 19개에서 16개가 됐습니다. 필요하면 `--profile ops` 로 되살립니다.

브로커는 줄이기 전에 전부 멈춰놓고 각 경로가 어디까지 버티는지 쟀습니다. 체결은 MySQL 원장이
네 번 모두 지켰고 호가는 수집기 버퍼가 10분까지 지켰습니다. 그 뒤 105개 파티션을 무정지로
재할당했고, 축소 후 재기동에서 브로커 응답 14초, 유실 0, 중복 239건(RMT 로 흡수), 그날 거래소
대조 6,803셀 전부 100% 를 확인했습니다. 받아들인 위험은 명확합니다. 브로커 1대 정지가 곧 전체
정지이고 10분을 넘기면 호가 유실이 시작됩니다. `dq_orderbook_gaps_daily` 가 그 결과를 셉니다.
자세한 것은 [docs/24](docs/24-broker-reduction-design.md) 에 있습니다.

### 아직 못 뺀 것

**ZooKeeper 112 MiB.** Kafka 3.x 에서 ZooKeeper 모드는 폐기 예고이고 4.0 에서 제거됐습니다.
KRaft 가 표준입니다. 두 가지가 막고 있습니다. 하나는 `cp-kafka 7.5.3`(Kafka 3.5)에서 제자리
마이그레이션(KIP-866)이 early access 라 7.6+ 이미지 업그레이드가 먼저라는 것이고, 다른 하나는
**이 Kafka 를 다른 프로젝트 두 개가 같이 쓴다**는 것입니다. 새 클러스터로 컷오버하면 그쪽
컨슈머 오프셋까지 이식해야 해서 별도 정지 창과 별도 검증이 필요합니다. 한 창에 한 가지만
바꾼다는 원칙에 따라 분리해 뒀습니다.

**Flink 잡 하나.** 체크포인트 상태 크기를 보면 어느 잡이 Flink 를 정당화하는지 드러납니다.

```
CDC Realtime Pipeline     3.36 MiB   289마켓 24시간 분 종가. 상태가 본체
Binance Depth Pipeline    0.27 MiB   심볼별 TreeMap 과 재동기화. 상태가 본체
Orderbook Pipeline        0.06 MiB   1분 윈도우
Binance Trade Pipeline    0.00 MiB   파싱과 싱크뿐
```

`Binance Trade Pipeline` 은 상태가 0 이라 Kafka Connect 싱크로도 됩니다. 이미 클러스터가 있어서
거기 둔 것이지 필요해서가 아닙니다. 반대로 이 클러스터를 다른 프로젝트와 같이 쓰고 있어서,
스트리밍 런타임을 프로젝트마다 띄우지 않는다는 이점은 있습니다.

## 값이 맞다는 것을 어떻게 아는가

`dq_` 로 시작하는 품질 표 9개가 매일 계산됩니다. 거래소 대조 두 종류, 적재 지연 분위수, 호가 공백 창,
수리 계보, 규칙 평가, 동등성, 원장 3자 대조, 그리고 수집 공백 라벨링입니다.

마지막 것은 설명이 필요합니다. 공백을 세는 것만으로는 사고인지 점검인지 알 수 없습니다. 거래소
점검 중에는 체결이 없는 것이 정상입니다. 그래서 거래소 공지 1,200건을 수집해 공백에 라벨을 붙였는데,
거래소가 붙인 점검 카테고리는 대부분 신분증이나 원화 입출금이라 거래를 멈추지 않았습니다.
카테고리로 걸렀으면 실제 거래 중단 8건을 놓쳤을 것입니다.

계약도 걸어뒀습니다. 컬럼 이름을 한 번 바꿨다가 대시보드 패널 10개를 죽인 적이 있어서, 소비자를
마주하는 모델 9개에 `contract: enforced` 를 붙였습니다. 컬럼 이름을 일부러 바꿔서 빌드가 실제로
멈추는지 확인했습니다. 증분 모델은 `on_schema_change=fail` 입니다. `append_new_columns` 는 조용히
늘린다는 뜻이라 계약의 취지에 반합니다.

토픽에도 JSON 스키마 계약이 있고, 검증기(`scripts/ops/validate-topic-schemas.py`)에는 `--self-test`
가 있습니다. 검증기가 위반을 실제로 잡는지 먼저 시험하지 않으면 통과만 하는 검증기가 됩니다.

## 틀렸던 것들

**필터 하나가 진짜 체결 3만 행을 버리고 있었다.** 모델마다 체결을 거르는 조건이 제각각이라 통일하려고
대조하다 발견했습니다. `op = 'c'` 만 통과시키고 있었는데 CDC 에는 스냅샷(`r`)과 백필도 있습니다.
6월 27일 두 시간 창에서 6,696행이 13,984행이 됐습니다. 그 창에서 체결의 52% 가 사라지고 있었습니다.
고친 뒤에는 늘어난 양이 원인과 정확히 일치하는지로 검증했습니다. `int_ohlcv_daily` 의 2월 13일이
186,388에서 209,488로 23,100 늘었는데 그날 `op='r'` 행 수와 같은 값입니다. 늘어난 것이 중복이 아니라
빠져 있던 진짜 체결이라는 증거입니다.

**3자 대조가 열린 날에는 항상 불일치였다.** 대시보드에 붙이자마자 5심볼 전부 빨강이었는데 실제
데이터는 멀쩡했습니다. 두 값의 측정 시각이 달랐던 것이고, 스냅샷과 실시간을 비교하고 있었습니다.
열마다 다른 기준 시각으로 상한을 걸어서 불일치를 0으로 만들었습니다. 거짓 경보를 내는 대조는 대조가
아닙니다. 사람이 곧 빨강을 무시하게 됩니다.

**부하 실험에서 병목은 Kafka 가 아니었다.** Binance 공개 체결을 녹화해 500부터 10,000 rows/s 까지
계단으로 재생했습니다. Kafka 는 무배치 acks=all 로 19k/s, 배치로 65k/s 가 나와서 파이프라인 계단의
100배에서 300배였습니다. 진짜 병목은 소스 체인에 묶인 동기 JDBC 싱크였고 근거 셋을 각각 측정했습니다.
정체 창이 ClickHouse insert 지연이 오른 분과 일치했고, 서브태스크 busy 가 inserts/s 곱하기 insert
지연과 맞았고, ClickHouse CPU 의 대부분이 머지였습니다. 싱크 배치를 200에서 1,000으로 바꾸자 정체
창이 5에서 0이 됐습니다. 유실 없이 실시간을 유지한 최대는 5,000 rows/s 로 관찰 주간 피크의 85배입니다.

**만든 것과 도는 것은 다르다.** 하루에 같은 유형을 다섯 번 만났습니다. DAG 네 개가 만들어진 뒤 한
번도 안 돌고 있었고, 재배포 스크립트는 옛 JAR 을 배포하면서 성공이라고 찍었고, 방화벽 스크립트는
한 번도 실행된 적이 없어 버그 두 개가 잠복해 있었고, Prometheus 대시보드 12패널이 통째로 빈 화면이었고,
cron 하나가 옛 비밀번호로 매분 403을 내고 있었습니다. 그래서 만들었다는 말을 스케줄 실행 이력,
전수 쿼리 실행, 자체 시험으로만 하기로 했습니다.

## 감시와 알림

알림은 세 층입니다. 10분마다 도는 헬스체크 12항목, 매시 도는 품질 SLO 판정, 주 1회 다이제스트입니다.
품질 게이트 임계를 0건이 아니라 90%로 둔 이유는, 얇은 마켓 한두 개가 순간적으로 조건을 못 맞추는
일이 늘 있고 그때마다 리포트를 막으면 사람이 게이트를 꺼버리기 때문입니다. 다만 중복 적재는 0건이
아니면 무조건 차단합니다. 정도의 문제가 아니라 사고입니다.

감시자는 다른 기계에 있습니다. 알림을 보내는 DAG 다섯 개가 전부 감시 대상인 미니 PC 안에서 돌고
있었는데, 그 기계가 죽으면 알림도 같이 죽습니다. 실제로 보안 하드닝으로 ClickHouse 포트를 로컬
바인딩으로 좁혔다가 바깥에서 감시하던 워크플로의 경로를 끊었고, 8시간 38분 동안 매분 에러만
쌓이고 알림은 0건이었습니다.

구조 자체도 문제였습니다. 그 감시자는 미니 PC 에 질의해서 최근 유입이 0인지 보는 pull 방식이라,
통째로 죽으면 질의가 실패해 판정에 도달하지 못합니다. 죽었다고 알리려면 죽은 쪽이 대답해줘야 하는
감시자였습니다.

포트를 다시 여는 대신 방향을 뒤집었습니다. 미니 PC 의 호스트 cron 이 5분마다 상태를 바깥으로
push 하고, 받는 쪽은 파일의 나이만 봅니다. 파일이 갱신되지 않은 것 자체가 신호라서 죽은 쪽의
협조가 필요 없습니다. 보내는 쪽을 Airflow DAG 이 아니라 호스트 cron 에 둔 것도 같은 이유입니다.
보내는 쪽은 감시 대상보다 의존성이 적어야 합니다.

훈련으로 확인했습니다. 송신을 끊고 임계 전에 두 번 조용한 것을 본 뒤, 899초 만에 판정이 나고
Slack 이 실제로 도착하는 것까지 쟀습니다. 재개 4초 만에 복구 알림이 왔습니다. 훈련 스크립트
(`scripts/ops/watchdog-drill.sh`)는 언제든 다시 돌릴 수 있습니다.

## 못 하는 것

이 항목이 있어야 나머지 숫자가 신뢰를 얻는다고 생각합니다.

- 규모가 크지 않습니다. 상시 수백에서 1,300 events/s 이고, 6.5억 행은 실무 기준으로 중간 규모의 하루치입니다. 규모 이야기는 부하 실험 문장으로만 합니다.
- 분산 처리를 해본 적이 없습니다. 단일 호스트, 단일 브로커입니다. 분산이 필요한 지점과 손댈 순서를 실측으로 안다고 말하지, 해봤다고 하지 않습니다.
- 가용성이 없습니다. 이 기계가 죽으면 전부 멈추고 복구는 수동입니다. 외부 감시자는 관측 가능성을 장애 도메인 밖으로 뺀 것이지 가용성이 아닙니다. 죽으면 15분 안에 안다와 안 죽는다는 다른 문장입니다.
- 대규모 배치를 운영한 적이 없습니다. DAG 11개와 dbt 모델 27개는 돌고 있지만 대규모가 아닙니다.
- Kafka 인증이 없습니다. 방화벽과 로컬 바인딩으로 막았고, SASL 은 클라이언트가 10곳 이상이라 미뤘습니다.
- 소비자가 저 자신입니다. 2층 원장과 케이스 관리로 소비자를 만들어 대조 대상을 만들었지만, 실제 이해관계자의 요구사항을 받아본 것은 아닙니다.

## 실행

```bash
cp .env.example .env     # 값을 채웁니다
docker compose up -d     # 기본 18개 서비스
scripts/build-flink-job.sh
scripts/startup.sh       # 토픽·커넥터·Flink 잡 등록
scripts/check-health.sh
```

`--profile ops` 를 붙이면 kafka-ui 와 Prometheus 가 같이 뜹니다. 평소에는 내려둡니다. Airflow
스케줄러 OOM 사고 때 Prometheus 360MB 가 대시보드 하나를 위해 떠 있었다는 것이 근거였습니다.
