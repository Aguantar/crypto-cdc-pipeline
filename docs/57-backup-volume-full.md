# 57. 오프사이트 백업 볼륨이 가득 차 전체 백업이 반만 갔다 (2026-10-28 ~ 10-30)

- 발견: 10-30 10:22 UTC 사용자 "뭔가 오류난 것 같아". 승격 채널에 `Backup Freshness` 2회(00:40, 06:10) 가 가 있었다.
- 영향: 원격 최신 복구 시점 10-28 (full_20261022 + incr_20261028). 10-29 전체 백업은 10,601 파일 중 9,850 만 도착, 10-30 증분·Parquet 10-28·10-29 미도착. 로컬에는 전부 있어 데이터 손실 없음.
- 원인: docs/51 의 보존 설계가 "동기화 뒤 정리" 라서 주 1회 전체 백업이 들어오는 순간 원격에 전체 3개가 공존한다. 전체가 16GB 일 때 세운 예산(106GB, 72%)이 지금 전체 28GB·증분 하루 6~7.5GB 로 자라 147GB 를 넘었다. 동기화가 실패하면 정리가 upstream_failed 로 아예 안 돌아 다음 날도 같은 자리에서 막힌다.

## 3. 왜 10-07 수정이 이걸 못 막았나

docs/51 §8 은 "전체 16GB × 2세대 + 증분 3일(하루 +1GB) + Parquet 60일 = 106GB(72%)" 로 잡았다. 틀린 가정 둘.
1. 전체 크기. 10-07 20.4GB → 10-22 29GB. Binance 30일 TTL 이 차면 24GB 로 봤는데 그보다 크다(Upbit 체결 365일·orderbook_1m 365일 표가 계속 자란다, D-1).
2. 증분 크기. "하루 +1GB" 가 아니라 6~7.5GB. 증분은 지난 전체 이후 바뀐 파트 전부를 담는데, 머지가 큰 파트를 다시 쓰므로 날이 갈수록 전체에 가까워진다(docs/51 이 지적한 바로 그 성질인데 수치를 낙관했다).
그리고 구조 결함: 정리가 동기화 뒤라 전체 3개가 잠깐 공존하는 순간의 용량(28×3 + 21 + 27 = 132GB + 부분)을 예산에 넣지 않았다. 85% 알림은 10-28 13:00 에 울렸지만 승격 대상이 아니었고, 다음 날 전체 백업이 한 번에 100% 로 밀어 넣었다.

## 5. 예산 재산정 (결정 대기)

실측 기준: 전체 28GB(주 1회, 2세대), 증분 하루 6~7.5GB(3일), Parquet 하루 0.85GB.

| 보존 | 정상 상태 | 전체 동기화 순간(사전 정리 뒤) |
|---|---|---|
| Parquet 60일(현행) | 56 + 21 + 51 = **128GB (87%)** | 28 + 28(들어옴) + 21 + 51 = 128 → 정리 뒤 128 |
| Parquet 45일 | 56 + 21 + 38 = **115GB (78%)** | 115 |
| Parquet 45일 + 증분 2일 | 56 + 14 + 38 = **108GB (73%)** | 108 |

현행 60일이면 정상 상태가 85% 알림선 위에 머문다(이번에 승격 대상에 넣었으므로 매일 휴대폰이 울린다). 45일로 줄이거나, 알림선을 90% 로 올리거나, 영구 보존 계층(Azure Blob Cold, docs/51 남은 결정)을 두는 셋 중 하나를 골라야 한다.

결정(10-30 10:58, 사용자 승인 "응 해봐"): Parquet 원격 보존 60 → **45일**(정상 상태 115GB, 78%). 커밋에 반영. 영구 보존 계층은 여전히 남은 결정.

## 6. 교훈
1. 용량 예산은 정상 상태가 아니라 **가장 부푸는 순간**(전체 교체 중 세대 수 +1)으로 세운다. 그리고 그 순간을 만들지 않도록 비우는 단계를 넣는다.
2. 증분 크기는 "하루 변경분" 이 아니다. 머지가 파트를 다시 쓰면 증분은 전체에 가까워진다. 10-07 에 알고도 수치를 낙관했다.
3. 알림이 있어도 가는 길이 틀리면 없는 것과 같다(docs/48 §7-2 와 같은 교훈). 용량 알림은 30회 울렸고 사람은 못 봤다. 이번에 승격 대상에 넣었다.
4. 실패한 태스크의 하류에 정리를 두면 실패가 실패를 부른다. 정리는 실패해도 돌아야 하는 쪽(동기화 앞)에 둔다.
