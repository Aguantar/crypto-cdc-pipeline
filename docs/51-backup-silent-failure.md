## 2. 원인

### 2-1. 증분이 매일 전체 크기로 자란다 (설계 가정 오류)

증분을 쓴 이유 (docs/21 §4, DAG 머리): 전체 백업이 당시 3.9GB 라 매일 보내면 월 120GB 가 되고, ClickHouse 네이티브 증분(`base_backup`)은 base 이후 바뀐 파트만 복사하므로 "첫 증분 80MB" 를 근거로 하루 수백 MB 로 산정했다. 용량 계산은 "Parquet 120일 87GB + 백업 20GB < 147GB" 였다.

틀린 지점: ClickHouse 증분은 **base 에 없는 파트**를 복사한다. MergeTree 는 백그라운드 머지로 파트를 계속 다시 쓰므로, base 이후 머지된 파트는 전부 "새 파트" 다. 월 파티션인 binance_trades(5.5억 행)와 crypto_trades 는 한 달 내내 머지되어 보름이면 거의 모든 파트가 base 와 달라지고 증분이 전체 크기에 수렴한다. 첫 증분 80MB 는 base 직후 하루치였을 뿐이고, 그 숫자 하나로 한 달을 외삽했다.

같은 성질은 LSM 계열 저장소(RocksDB·Cassandra SSTable 등) 공통이다. 컴팩션이 파일을 다시 쓰는 저장소에서 "파일 단위 스냅샷 증분" 은 작게 유지되지 않는다.

### 2-2. 원격 보존 정책이 3개월치를 들고 있게 한다

`apply_remote_retention` 은 전체 백업 3세대를 남기고 **가장 오래된 남은 전체보다 오래된 증분만** 지운다. 전체가 월 1회이므로 3세대 = 3개월, 그 사이 증분은 전부 남는다. 2-1 과 결합하면 월 400GB 가 넘는 설계였다.

### 2-3. 실패가 성공으로 찍혔다 (`| tail -6`)

```
rsync -a ... /backups/ ubuntu@…:/mnt/backup/clickhouse/ 2>&1 | tail -6
```

파이프라인의 종료 코드는 마지막 명령(tail)의 것이다. rsync 가 code 11 로 죽어도 태스크는 0 으로 끝난다. `set -o pipefail` 이 없었다. 로그에는 "No space left on device" 가 6일 동안 매일 찍혀 있었다.

### 2-4. 검증 태스크가 실패하는 태스크 뒤에 있었다

`sync → apply_remote_retention → prune_local → verify_remote_in_sync`. 검증(dry-run rsync 로 전송 대상 0 확인)은 이 사고를 정확히 잡는 장치였다. 그런데 prune_local 이 10-02 부터 권한 문제로 실패하자 검증은 upstream_failed 로 한 번도 돌지 않았다. 검증을 정리 작업에 종속시킨 것이 실수다.

### 2-5. prune_local 은 한 번도 성공한 적이 없다 (권한)

ClickHouse(uid 101)가 만드는 백업 디렉터리는 750 이다. Airflow(uid 50000, 보조 그룹 101)는 읽을 수는 있어도 지울 수 없다(부모 디렉터리에 그룹 쓰기 없음). 09-17 이후 삭제 대상이 처음 생긴 날이 10-02 였고(14일 보존), 그날 처음 실행된 경로가 처음 실패했다. "쓴 스크립트는 돌려 봐야 스크립트" (docs/48 교훈)의 재현이다.

### 2-6. 아무도 "백업이 원격에 도착했나" 를 묻지 않았다

헬스체크는 적재·파생 표·cron 생존을 보지만 백업 도착 신선도는 보지 않는다. docs/48 §3 의 "살아있나와 맞나는 다른 질문" 이 백업 경로에서 그대로 반복됐다. 백업 DAG 의 태스크 실패 콜백은 prune_local 실패로 매일 울렸어야 하는데, 일반 채널의 알림을 사람이 보지 않았다(09-30 수집기 정지와 같은 유형).

## 3. 실무에서도 흔한가

흔하다. 이 사고는 알려진 범주 다섯이 겹친 것이다.

| 범주 | 이 사고 | 일반적인 형태 |
|---|---|---|
| 백업 성공의 정의가 "명령이 돌았다" | rsync 종료 코드 삼킴, 검증 미실행 | "백업은 복원해 보기 전까지 백업이 아니다". GitLab 2017 사고가 대표 사례(백업 수단 다섯 개가 전부 동작하지 않았음이 삭제 뒤에 드러남) |
| 파이프가 종료 코드를 가린다 | `cmd \| tail` | 셸 스크립트의 고전적 함정. `set -euo pipefail` 이 기본 처방 |
| 증분·스냅샷 크기 가정 | 첫 증분 80MB 를 외삽 | 컴팩션·머지가 있는 저장소에서 파일 단위 증분은 작게 유지되지 않는다 |
| 보존 정책과 용량의 불일치 | 3세대 × 월 = 3개월 | 보존은 "며칠" 이 아니라 "몇 GB" 로도 검산해야 한다 |
| 검증이 다른 실패에 가려짐 | verify 가 prune 뒤 | 검증은 가장 먼저 또는 독립 트리거로. 정리 작업은 검증 결과를 바꾸지 않는다 |

차이가 있다면 실무는 백업 모니터링(마지막 성공 백업 시각 SLO, 저장소 사용률 알림, 주기적 복구 리허설)이 체크리스트에 있고 담당자가 있다는 것이다. 여기엔 셋 다 없었다.

## 5. 교훈

1. 외삽하지 않는다. 첫 날 숫자는 첫 날 숫자다. 증분 크기는 일주일 추이로 보고 정한다.
2. 보존 정책은 날짜와 GB 둘 다로 검산한다.
3. 파이프 뒤의 명령이 종료 코드를 정한다. BashOperator 는 `set -euo pipefail` 부터.
4. 검증은 정리에 종속시키지 않는다.
5. 백업에도 신선도 SLO 가 있어야 한다. "마지막으로 원격에 도착한 백업이 언제인가" 를 매일 묻는다.
