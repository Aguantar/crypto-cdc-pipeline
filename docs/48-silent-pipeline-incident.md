## 2. 원인 다섯 개

### 2-1. `dbt_test` 가 09-10 부터 매일 실패

09-10 ~ 09-18 실행 전부 `dbt_test` 가 3회 재시도 후 실패, 하류(`quality_gate` → `generate_report` → `slack_daily_report`)는 `upstream_failed`.
실패한 테스트는 `assert_no_long_gaps` 와 `assert_positive_volume` 둘이고, 둘 다 09-20 에 거짓 경보로 판정해 SQL 을 고쳤다.
고친 SQL 은 맞았다. 09-24 에 DAG 과 같은 명령으로 돌리면 둘 다 통과한다. 문제는 고치면서 DAG 실행 이력을 보지 않았고,
수동 실행으로 통과를 확인한 뒤 스케줄된 `dbt_test` 가 열흘째 죽어 있다는 것을 몰랐다는 점이다.

### 2-2. `dbt_run` 이 09-20 16:13 부터 매일 실패 - 계약 도입

09-20 에 소비자용 모델 9개에 `contract: enforced` 를 걸었다. 그날 첫 스케줄 실행부터 6개 모델이 컴파일 오류였다.

```
| column_name  | definition_type | contract_type          | mismatch_reason    |
| binance_base | String          | LowCardinality(String) | data type mismatch |
```

원인은 어댑터 버전이었다. 컨테이너의 dbt-clickhouse 1.7.2 는 계약 타입을 비교할 때 `Nullable`·`LowCardinality` 수식자를 벗기고 비교한다.
그래서 yml 에 물리 타입 그대로 적으면 영원히 불일치다. 반대로 수식자를 벗겨 적으면 DDL 이 yml 타입 그대로 만들어져 물리 타입이 바뀌고,
`dim_markets.delisting_date` 의 NULL 287/289 행이 `1970-01-01` 이 된다(09-24 01:27 실측). 어느 쪽도 답이 아니었다.

"빌드가 멈추는 것을 확인했다" 는 09-20 의 기록은 호스트에 따로 설치된 dbt(core 1.11.6, clickhouse 1.10.0)로 돌린 결과였다.
새 어댑터는 수식자 있는 계약을 제대로 다룬다. 같은 yml 이 스케줄 실행(컨테이너, 1.7.2)에서는 매일 실패했다.

### 2-3. `depends_on_past` 와 `max_active_runs=1` 의 양방향 대기

09-20 에 "전날이 실패했는데 오늘이 돌면 증분에 구멍이 남는다" 는 이유로 `depends_on_past=True` 를 걸었다.
09-19 의 `dbt_run` 이 실패한 채 남으니 09-20 은 영원히 대기한다. 여기까지는 의도한 동작이다.
몰랐던 고리는 `max_active_runs=1` 이다. 대기 중인 09-20 run 이 `running` 으로 유일한 슬롯을 물고 있어, 재시도하려고 clear 한 09-19 run 이
`queued` 에서 나오지 못한다. 09-20 은 09-19 를 기다리고 09-19 는 09-20 이 끝나기를 기다린다.
실패한 날이 하나 생기면 그 뒤 모든 날이 사람이 풀기 전까지 멈추는 구조다. 09-24 에 `depends_on_past` 를 뺐다.
구멍은 실패한 날을 다시 돌려 메우는 것이고, 표가 굳는 것은 아래 4-3 의 신선도 점검이 잡는다.

### 2-4. `cases_hourly` 가 09-22 부터 `KeyError: LEDGER_MYSQL_PASSWORD`

환경 변수를 compose 의 `airflow-init` 에만 넣었다. LocalExecutor 는 스케줄러 프로세스가 태스크를 돌리므로 스케줄러 env 에 있어야 한다.
09-20 스케줄러 재생성 뒤 처음으로 DB 에 닿는 순간(09-22 06:20)부터 실패했다.

### 2-5. SLA 콜백이 매 처리 주기 예외

Airflow 2.8 은 `sla_miss_callback` 의 `task_list` 를 객체 목록이 아니라 개행으로 이은 문자열로 넘긴다. 객체 목록을 가정한 코드가 09-20 부터
나흘간 처리기 로그에만 33,260줄(하루 45회)을 쌓았다.

## 3. 왜 아무도 몰랐나

- 다른 기계의 외부 감시자는 "미니 PC 가 살아있나, 원본이 들어오나" 를 본다. 둘 다 정상이었으니 제대로 조용했다.
- 파생 표가 갱신되는지는 아무도 보지 않았다. dbt 가 나흘 죽어도 Airflow 는 멀쩡하고 적재도 멀쩡하니 어디서도 울리지 않는다.
- 태스크 실패 콜백은 등록돼 있었지만 로그·스케줄러·`callback_request` 어디에도 실행 흔적이 없다. Slack 헬퍼가 실패할 때만 로그를 남겨,
  매일 정상 발송돼 조용한 것인지 아예 안 돈 것인지 구분할 수 없었다.

## 5. 복구 중 드러난 것

### 5-1. ClickHouse 총 메모리 경합의 실제 식

복구 중 `int_ohlcv_1h` 가 두 번(00:49, 16:01) `Memory limit (total) exceeded` 로 죽었다. 쿼리 자체는 450 ~ 500 MiB 로 한도 안이다.
`system.metric_log` 로 초 단위 총량을 보니:

| 항목 | 값 |
|---|---|
| 쿼리·머지 없을 때의 기준선 | median 723 MiB (캐시 27 MiB, 사전 0 - 나머지의 정체는 미분해) |
| 머지 버스트 | 최대 598 MiB (동시 머지 5 ~ 6, `binance_orderbook_raw` 는 시간당 12,000회) |
| 서버 한도 | 1.57 GiB |

기준선 + 머지 버스트 + dbt 모델(500 ~ 800 MiB)이 겹치는 순간 OvercommitTracker 가 가장 큰 "죽일 수 있는" 쿼리를 고르고, 그것이 dbt 모델이다.
00:49 에는 총량이 2.40 GiB 까지 갔다. 모델 순서를 바꾸거나 직전 모델을 제한하는 것으로는 막을 수 없다.

첫 처방은 틀렸다. 외부 GROUP BY 스필을 붙였더니 조각 11,562개를 다시 합치며 1.12 GiB 로 더 크게 죽었다. 맞는 처방은 항 하나를 없애는 것이었다.
`int_ohlcv_1h` 는 매일 1.28억 행을 FINAL 로 다시 묶어 09-25 이후 것만 바뀌는 표를 통째로 만들고 있었다. 파티션 키로 33시간 창을 잘라
delete+insert 로 교체하니 읽는 행 663만, 90 MiB, 0.8초다.

### 5-2. `FINAL` 의 비용

09-20 에 `stg_trades` 에 FINAL 이 붙은 뒤 이 모델은 55 MiB / 10초에서 550 MiB / 15초가 됐다. 1.28억 행 39 파트를 FINAL 로 읽는 비용이다.
중복을 저장소에서 흡수하기로 한 대가가 여기서 나온다. 전체 이력을 매일 읽는 모델은 FINAL 과 같이 쓰면 안 된다.

### 5-3. 두 DAG 이 같은 모델을 동시에 빌드하면 깨진다

`rules_daily`(01:15) 와 `daily_pipeline` 재시도가 겹쳐 `int_volume_surge_daily__dbt_backup already exists`. 평소엔 16:00 과 01:15 라 안 겹쳤을 뿐이다. 풀 `dbt` 1슬롯이 답이다.

## 8. 교훈

1. 완료는 스케줄 실행 이력으로만 말한다. 수동 실행의 통과는 "그 도구, 그 순간" 의 통과다.
2. 도구는 컨테이너 안의 것만 쓴다. 호스트의 다른 버전 dbt 가 "통과" 를 만들었고 `target/` 소유까지 어긋나게 했다.
3. 살아있나와 맞나는 다른 질문이다. 원본 적재 감시는 파생 표의 정지를 못 본다. 표마다 "언제 마지막으로 갱신됐나" 를 물어야 한다.
4. 사건과 상태를 구분한다. 같은 상태를 10분마다 다시 보내면 사람이 알림을 끈다.
5. 자원이 빠듯한 저장소에서는 "쿼리 한도" 가 아니라 "총량 - 기준선 - 버스트" 가 예산이다.

## 9. 남은 것

- 기준선 700 MiB 의 정체. Kafka 엔진 표 6개의 소비자 버퍼와 파트 791개의 메타로 추정하지만 재지 않았다.
- `int_venue_hourly_close`(788 MiB)·`int_alert_transitions_recomputed`(699 MiB)는 여전히 전체 이력이다. 같은 경합에 걸리면 증분으로 가거나 한도를 올린다.
- 급등 구간 손실(7)의 대책은 미정이다. 수집기의 지연을 지표로 내보내 "지금 잃고 있다" 를 알리는 것이 먼저다.
