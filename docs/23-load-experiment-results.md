- **판정**: 임계점은 5,000/s 와 10,000/s 사이. 10,000/s 에서 백프레셔 지표는 0 이었지만(소스가 체인의 머리라 백프레셔를 받을 상류가 없다) **소스 체인 busy 가 1.0 에 닿았고**, 적재율이 387/s 까지 떨어지는 정체 5회, 그 사이 e2e 가 36초까지 밀렸다가 13,035/s 로 따라잡는 톱니가 생겼다. 유실은 없지만 "실시간"이 아니다.
- **병목 = 소스 체인에 묶인 동기 JDBC 싱크, 그리고 파티션 편중**. 근거: (1) 정체 창은 CH insert 평균 지연이 9→24~34ms 로 오른 분(04:40, 04:44~46)과 일치. ClickHouse 자체는 예외 0, 메모리 한도 로그 0, insert max 469ms 라 "막힌" 것이 아니라 "느려진" 것. (2) 서브태스크 busy ≈ inserts/s × insert 지연. 10k/s = 배치 200행 = 50 inserts/s, 파티션 3개를 서브태스크 2개가 나눠 서브태스크 0 이 33 inserts/s × 34ms ≈ 1.1 s/s → 포화(실측 busy 0.90 vs 0.65). (3) ClickHouse CPU 100%+ 의 대부분은 머지: 10분간 NewPart 29,933 / MergeParts 7,440(합 519초 = 0.87코어 상시). 파트 50개/s 를 만드는 것이 곧 배치 200행이다.
- **선행 지표**(임계 전 계단에서 먼저 움직인 것): ① 소스 busy 48→76→126→240 ms/s(500→5,000/s, 선형) - 1,000 에 닿기 전에 경보 가능. ② ClickHouse 메모리 0.99→1.23→1.65 GiB(한도 1.75) - 5,000/s 에서 이미 94%. ③ CH insert 평균 지연(9ms 기준선 → 24ms 부터 정체 시작). 셋 중 ①·③ 을 알림으로 승격한다(§6).
- **"현 구성 여유 N배"**: 유실 없이 실시간(e2e p95 < 5s)을 유지한 최대 계단은 **5,000/s = 관찰 주간 피크 시(59 rows/s)의 85배, 평균(25)의 200배**. 10,000/s 도 유실은 없으나 지연 SLO 를 깬다.

| 브로커 단일 컨테이너 스파이크(80%+) | 관찰 주간(09-09~15) 5분 표본의 **37.3%**(730/1,957)에 이미 존재, 오늘 50%(17/34) | 대부분 평소 행동(복제 fetch·세그먼트·GC 버스트). 실험이 빈도를 조금 올림 |

결론: 정체의 주 원인은 실험(소스 체인 포화 + 머지 CPU)이지만, **정체가 "언제" 터지는지는 동거 부하(MySQL 정리 주기)가 정했다**. 그래서 이 숫자는 "이 호스트에서의 임계"이고 컴포넌트 고유 상한이 아니다 - 같은 사양 스테이징이 없는 대가.

### 5-2. 개선 1건 + S4 전후표 (같은 입력: Binance 코퍼스 10,000/s × 10분)
개선: JDBC 배치 200 → **1,000행** (`CLICKHOUSE_BATCH_SIZE` env, 실험 잡만; 프로덕션 기본 200 불변). 3초 간격 상한은 그대로.

| 지표 | 전 (배치 200, 04:38~04:48) | 후 (배치 1,000, 04:53~05:03) |
|---|---|---|
| 유실 / 중복 | 0 / 0 | 0 / 0 (5,999,966 = 적재 = uniq) |
| 정체 창(30초 적재율 < 9,000/s) | **5** (최저 387/s) | **0** (경계 창 2개 제외: 시작·종료 램프) |
| e2e p50 / p95 / max | 0.06 / **26.5 / 36 s** | 0.11 / **0.28 / 1.56 s** |
| 계단 끝 적체 | 49,508 (5s분) | 15,812 (1.6s분) |
| 소스 체인 busy p50 / max | 651 / **1,000** ms/s | **200** / - |
| CH insert 수·평균·p95 | 50/s · 9~34 ms · 25~100 ms | **10/s** · 6~12 ms · 14~44 ms |
| CH 파트 생성 / 머지 (10분) | 29,933 / 7,440 (519 s) | **6,222 / 1,365 (98 s)** |
| CH CPU p50 / 메모리 max | 103% / **1.735 GiB** | **28%** / 0.99 GiB |
| lab TM 힙 max | 758 MiB | 805 MiB |
| load1 p50 / max | 11.1 / 14.2 | 6.7 / 10.3 |
| 프로덕션 KRW e2e p95 / 가드 max | 4.74 s / 5.62 s | 4.51~4.76 s / 7.54 s |

- 왜 효과가 있나: 서브태스크 busy ≈ inserts/s × insert 지연. inserts/s 를 1/5 로 줄이니 busy 651→200. 파트 생성률도 1/5 이라 머지 CPU(0.87코어→0.16코어)가 사라지고, 그 CPU 가 insert 지연을 다시 낮춘다(34→12ms). 하나의 변경이 두 병목(싱크 포화·머지 CPU)을 같이 푼 이유는 둘 다 "초당 insert 문 수"에서 나왔기 때문이다.
- **"현 구성 여유 N배" (확정)**: 배치 200(현 프로덕션 설정)은 **5,000/s = 피크 85배**까지 실시간, 배치 1,000 은 **≥ 10,000/s = 피크 170배**(상한 미측정, 코퍼스 소진). 두 문장 다 "이 호스트(4코어, 26컨테이너 동거)에서".
- 프로덕션에 배치 1,000 을 적용하나: **지금은 안 한다.** 프로덕션 유입은 피크 59 rows/s 라 3초 간격 안에 배치 200 도 차지 않는다(최대 ~180행). 바꿔도 오늘 효과는 0 이고 재배포 정지 창만 든다. 지속 유입이 2,000/s 를 넘는 날(호가 확장·거래소 추가)에 적용한다 - 근거는 이 표.

### 5-3. 어디서 걸렸고, 실무에서도 흔한 지점인가 (사용자 질문)
"흔한가"는 일반 실무 지식이지 측정치가 아니다.

| # | 어디서 | 우리 실측 | 실무에서 | 실무 해법 |
|---|---|---|---|---|
| 1 | Flink 소스 체인의 동기 JDBC 싱크(source→parser→sink 가 한 스레드로 체인) | busy 1.0, insert 지연 9→34ms 에 정체 | 매우 흔함. 싱크가 소스와 체인되면 싱크 지연이 곧 소비 지연 | 배치 확대(S4), 싱크 체인 분리(`disableChaining`/rebalance), 비동기 싱크 API |
| 2 | Kafka 파티션 ↔ Flink 병렬도 불일치(3/2) | 서브태스크 0 이 2파티션, busy 0.90 vs 0.65 | 흔함. 병렬도가 파티션 수의 약수가 아니면 반드시 생김 | 파티션 수를 병렬도의 배수로 |
| 3 | ClickHouse MergeTree 소량 insert(200행 = 파트 50개/s) | 머지 7,440회·519초, CPU 100%+ | 매우 흔함. 공식 가이드가 insert 당 1,000행 이상 권장, "too many parts" 가 대표 장애 | 배치 확대, `async_insert`, Buffer 테이블 |
| 4 | MySQL 정리 DELETE + CDC(binlog→Debezium→토픽으로 번짐) | 10분마다 4만 건, MySQL 51%, 정체 시각과 일치 | 흔함. CDC 붙은 테이블의 대량 DELETE 는 binlog 폭주의 단골 | 파티션 DROP(행 단위 binlog 없음), 삭제 이벤트 필터, 비피크 스케줄 |
| 5 | Kafka 브로커 1대 정지 | 리더 이동 1분만 p95 7.7s, 무손실, ISR 15초 회복 | 흔하고 설계된 상황(RF3/minISR2/acks=all) | 그대로. 브로커 1대로 줄이면 이 보호가 사라짐 |
| 6 | 단일 호스트 과점유(load1 14 / 4코어) | 정체 "시각"을 동거 부하가 결정 | 드묾 - 동일 사양 스테이징에서 실험 | 스테이징 분리. 우리는 창·가드·기록으로 축소 |

측정 쪽 함정: 컨슈머 lag 톱니(체크포인트 커밋 → Flink 자체 지표나 "발행−적재"로), Kafka CLI JVM 의 브로커 CPU 오염(JMX exporter 로), pgrep/pkill 자기 셸 매칭. 셋 다 실무에서 자주 헷갈리는 지점이라 docs/18 에도 올렸다.

남은 것:
- 브로커 3→1 + KRaft(docs/19 #12): S3 가 "복제가 실제로 지켜 준다"를 보였으므로, 1대로 줄이면 그 보호가 사라진다. 축소 전에 "브로커 전체가 없는 3분"을 실측한다(`pipeline-load-lab/replay/scenario_all_brokers_stop.sh`, 사용자 실행).
  - 왜 이 질문이 본질인가(사용자 통찰, 09-17): **호가가 되돌릴 수 없는 데이터다.** 체결은 MySQL 원장 + 거래소 REST 이력의 이중 안전망이 있어 실패가 "지연"으로 끝나지만, 호가는 거래소 이력 API 도 우리 원장도 없어 못 받은 순간 영구 유실이다. 그런데 호가 경로가 더 얇았다(수집기 → Kafka 직행, 버퍼 120초, 대조 수단 없음). 브로커 수는 부차적이고 "호가를 어디까지 지킬까"가 결정이다.
  - 실측 전에 넣을 수 있는 것 2건은 넣었다: ① `dq_orderbook_gaps_daily` - 초당 스냅샷 0 인 구간을 유실 창으로 기록(30일 전수에서 09-12 06:20:31 +6초 1건, 원인 불명), ② `health_check` 가 FAILED Connect 태스크를 자동 재시작(정지 뒤 체결이 MySQL 에 쌓인 채 멈추는 것을 막는다; 실제 FAILED 경로는 실측에서 처음 밟는다).
  - 실측(§7) 결과로 정한 것: 호가 수집기 타임아웃 600초 + 메타데이터 전파 대기 300초 + produce 예외 처리(§7-1).
- 호가 파이프라인 계단(docs/15 ① 호가 250→1,000/s)은 미실행. 체결과 같은 싱크 구조라 같은 병목이 예상되지만 실측은 아니다.
- 배치 1,000 의 상한(10k 이상)은 코퍼스가 더 필요하다(Binance 월별 파일).
